> 本文把两件事合在一起讲：一份是 L8《首席工程师的 Agentic Engineering 工作流》视频笔记（Kun Chen 主讲），另一份是我自己经过多轮迭代后定型的终端工作流。视频提供方法论骨架，我的配置是它的一个具体实例——从"造船"到"掌舵"的完整落地记录。

---

## 一、为什么值得专门优化一遍 Workflow

L8 课程开篇把人比作**船长**，把 coding agents 比作**船员**，把终端、会话管理、记忆、Skills、验证流水线与并行调度组合成一艘船。评价标准随之从"模型能不能写出代码"，提高为三个问题：

- 任务能否被正确理解？
- 过程能否隔离？
- 结果能否验证？

这三问构成了我优化工作流的出发点。课程给出了一条**五步认知地图**：

1. **先造船** —— 低摩擦、可恢复的终端工作环境
2. **Onboarding** —— 上下文分层（全局记忆 → 项目记忆 → Skills）
3. **单代理协作** —— 工具接口、验证流水线
4. **多代理并行** —— worktree 隔离、资源池
5. **First Mate** —— 统一调度与控制平面

顺序很重要：没有可靠的工作环境和上下文分层，直接增加代理数量只会把局部问题放大成并行混乱。所以我的优化从"造船"开始，也就是下面这套终端架构。

## 二、先造船：终端最终架构

视频里 WezTerm 负责可编程、跨平台的终端外壳，tmux 负责工作分区与持久会话。落到我的机器上，完整架构是这样的：

```
Windows
│
└── WezTerm                     ← 最外层工作台
    │  Leader = Alt + W
    │
    ├── PowerShell 7            ← Windows 工作
    │   ├── Oh My Posh
    │   ├── PSReadLine
    │   ├── z / zi
    │   ├── y
    │   ├── fd / rg / fzf
    │
    └── WSL Ubuntu              ← Linux 开发
        │
        ├── Bash
        ├── z / zi / y
        ├── fd / rg / fzf
        │
        └── tmux                ← 项目工作区
             Leader = Ctrl + A
             ├── Agent
             ├── Yazi
             ├── Test
             ├── Server
             └── Logs
```

整个配置可以压缩成两句话：

> **WezTerm 管环境，tmux 管项目。**
> **z/zi/y 管去哪，fd/rg 管找什么。**

### 2.1 WezTerm：最外层控制器

WezTerm 的配置本身就是代码（Lua），支持平台条件、窗口参数、回调与快捷键写在同一份文件里，还能热重载——**把环境定制变成可快速试验的工程过程**。

我的 Leader 键是 `Alt + W`，注意是两段式按键：

```
Alt+W  →  松开  →  再按第二个键
```

核心快捷键：

| 操作 | 快捷键 |
|------|--------|
| Launcher | Alt+W → Space |
| Command Palette | Alt+W → p |
| 新 Tab | Alt+W → c |
| 左右分 Pane | Alt+W → \ |
| 上下分 Pane | Alt+W → - |
| 移动 Pane | Alt+W → h/j/k/l |
| Pane 最大化/恢复 | Alt+W → z |
| 关闭 Pane | Alt+W → x |
| 全屏 | Alt+Enter |

`Alt+W → p` 值得单独说：它相当于 WezTerm 版的 Ctrl+Shift+P。**忘记某个功能时直接搜**：split、pane、tab、zoom、launcher、workspace、copy、font。

### 2.2 每天打开终端，先判断做什么

刻意不形成"打开终端 = 一定先进 tmux"的肌肉记忆。tmux 是给**长期项目会话**用的，临时任务不该为它付出上下文切换成本：

| 我要做的事情                    | 推荐入口                          |
| ------------------------- | ----------------------------- |
| Windows 上临时执行命令           | 直接 PowerShell                 |
| Git、小脚本、小型 Codex 任务       | PowerShell                    |
| 看 Windows 文件              | PowerShell → y                |
| 正式 Linux 开发               | Alt+W → Space → tmux · Ubuntu |
| 临时用一下 Ubuntu              | Alt+W → Space → WSL · Ubuntu  |
| 长时间 Agent / Server / Test | Ubuntu + tmux                 |
| SSH 到服务器 / VM             | WezTerm → SSH → 远端 tmux       |

## 三、跨平台工具层：一套命令，两个系统

这是当前配置最舒服的地方：PowerShell 和 Bash 里保持同一套高频命令，不必切换。

| 命令 | 含义 | 心智模型 |
|------|------|----------|
| `z xxx` | 智能跳到常用目录 | 我知道去哪 |
| `zi` | 模糊选择目录 | 我大概知道去哪 |
| `y` | Yazi 文件浏览器 | 我想看看有哪些文件 |
| `fd xxx` | 按文件名查找 | 文件叫什么？ |
| `rg xxx` | 按文件内容搜索 | 文件里面写了什么？ |
| `fzf` | 通用模糊选择器 | 给我一个选择界面 |

### 3.1 z / zi：替代大量手敲 cd

zoxide 会学习访问历史，所以刚开始 `z xxx` 可能不够聪明，**用几天后会越来越准**。以前写 `cd D:\Work\Projects\Agent-Memory\project`，现在一个 `z memory` 就够了。记不清具体路径时用 `zi`，输入 `kyl` 即可过滤出 kylin 相关目录再选择。

### 3.2 y：可视化的 cd

Yazi 最值得用的模式是浏览 → 退出跟过去：

```
y  →  进入 ~/work/kylin-memory/project  →  q
```

`q` 退出时 shell 自动 cd 到 Yazi 最后停留的目录，`Q` 退出但不改变目录。所以 Yazi 本质上是**可视化 cd**。

### 3.3 fd / rg：寻找

- "competition-v2 那个目录在哪？" → `fd competition-v2`
- "哪些地方引用了 competition-v2？" → `rg "competition-v2"`

所以是：**fd = Find file，rg = Ripgrep content**。

## 四、tmux：项目工作区

课程讲 tmux 的三层结构：session 包含多个 windows，window 可切分成多个 panes。映射到我的使用习惯：

- **Session = 项目工作区**（如 `kylin-memory`）
- **Window = 一类任务**（dev / test / logs）
- **Pane = 同一任务页的分屏**（Agent / Yazi / shell）

### 4.1 快捷键（Leader = Ctrl + A）

| 操作 | 快捷键 |
|------|--------|
| 新 Window | Ctrl+A → c |
| 左右分 Pane | Ctrl+A → \| |
| 上下分 Pane | Ctrl+A → - |
| 移动 Pane | Ctrl+A → h/j/k/l |
| Pane 最大化 | Ctrl+A → z |
| Detach | Ctrl+A → d |
| Reload config | Ctrl+A → r |
| 关闭当前 Pane | Ctrl+A → x |
| 关闭 Window | Ctrl+A → & |
| Copy mode | Ctrl+A → [ |

### 4.2 一个项目的默认布局

可以固定成三块：左 = 长期 Agent，右 = 文件浏览，下 = git / test / build。

```
Window 1: DEV
┌────────────────────────────┬───────────────────┐
│ Agent (Codex / Hermes)     │ Yazi              │
├────────────────────────────┴───────────────────┤
│ Shell / Git / Test                             │
└────────────────────────────────────────────────┘
```


### 4.3 "退出"一定要区分

| 意图           | 操作                          | 结果                              |
| ------------ | --------------------------- | ------------------------------- |
| 暂时离开，后台继续    | `Ctrl+A → d`（detach）        | 项目仍然存在                          |
| 回来           | `tmux attach -t main`       | 恢复现场                            |
| 当前 pane 真正退出 | `exit` 或 `Ctrl+A → x`       | 只结束当前 pane                      |
| 杀整个 session  | `tmux kill-session -t main` | 该 session 全部结束                  |
| 杀所有 tmux     | `tmux kill-server`          | 所有 session/window/pane 全部结束（谨慎） |

**关 WezTerm 时发生了什么**：普通前台 shell 会跟着结束；但程序在 tmux 里时，关掉 WezTerm 只是断开 client，tmux server 和里面的 Agent/Server **继续运行**。所以想保留现场就 detach 再关窗口；不想后台运行就先结束任务再 kill session。

### 4.4 SSH / VM 场景

```
ssh user@server
tmux new -A -s project
```

即使 SSH 断线，tmux 任务继续；重新连上后 `tmux attach -t project` 恢复。对经常做 Linux/VM/ssh项目开发的工作方式，这个方法很好。

## 五、上下文治理：把知识放到正确的加载层级

视频的核心观点：**全局记忆是每次请求都要缴纳的成本**。全局文件应该极短（讲者的 AGENTS.md 只有 27 行），只放稳定偏好与反复出现的模型偏差；项目背景、一次性约束和大段操作说明不应常驻。

对应到我的 Agent 工作流（Hermes / Codex），分层口径是这样的：

| 层级 | 存什么 | 触发方式 |
|------|--------|----------|
| 全局记忆 | 稳定偏好、反复出现的纠错 | 每次会话常驻（保持极短） |
| 项目记忆 | 项目定义、技术栈、术语、约定 | 进入项目时加载 |
| Skills | 条件化流程、操作知识 | **渐进式披露**：只暴露短 description，任务匹配后才读正文 |

渐进式披露（progressive disclosure）是其中最关键的一环：E2E 指令只在改代码与验证行为时有用，普通问答每次加载整段说明只会浪费 token 并干扰注意力。分层既是省 token，也是**减少无关指令竞争模型注意力**。

另一个实践：项目记忆的正确增长方式不是一次写满，而是——**代理犯错 → 人类给出具体纠正 → 把可复用教训写回项目记忆**，让后续会话直接继承。一次纠错变成集体经验，这是项目记忆区别于静态 README 的地方。

## 六、从"代码完成"到"变更可信"

Agent 产码速度远快于人的逐行审查速度。如果所有变更都要求同等深度的 diff review，**人的时间就是硬上限**。视频的建议是把审查预算投向更高信号的位置：意图、证据、风险。

落到日常，我的最小验证习惯：

```bash
git status        # 我改了什么
git diff --stat   # 改动规模多大
git diff          # 具体改了什么
git branch --show-current   # 当前分支
git log --oneline --decorate -10   # 最近提交
```

Agent 修改完代码后，至少跑一遍这三条再决定是否接受。进阶版是课程里 **No Mistakes 流水线的骨架：隔离 worktree → fresh context 做对抗性审查 → 自动修复明确问题、产品歧义升级给人 → E2E 记录证据 → PR。**

> **E2E（end-to-end，端到端）**：指从用户的真实使用路径出发验证整个流程，而不是只测某个函数或模块。比如"修复 bug"的 E2E 是——先模拟用户实际会走的操作路径复现问题，实施修复后再按同一条路径验证问题消失。它防止局部测试掩盖真实故障路径：单元测试保证零件没问题，E2E 保证整条流水线真的通。

> PR 不只交付代码，还应交付决策材料：Intent、What Changed、Testing、evidence、risk assessment。人先看"是否满足原始意图的直接证据"，再审计自动修复是否越界，最后按风险等级决定 diff 审查深度。

## 七、长任务与并行：自治必须有边界

### 7.1 长任务的三重边界

"人守两端，AI 承担中间"——人的集中投入在任务开头（意图）和结尾（验收），中间连续执行交给代理。但长运行不等于无限运行，安全的长任务（loop）必须同时有：

1. **语义停止条件**（semantic stop）—— 明确"做完"长什么样
2. **迭代上限**（iteration cap）—— 最多循环多少轮
3. **Token 上限**（token cap）—— 资源护栏

还要保留分支/worktree 和人工检查点。适合长循环的任务通常有外部可观察指标、单轮成败可判定、每轮结果可独立提交、错误可回滚——页面性能、E2E 覆盖率、指标驱动假设实验都是典型例子。

### 7.2 并行：隔离、资源池、控制平面

多代理并行有三个前提，缺一个都会把执行等待换成人的上下文切换：

| 条件   | 解决的问题           | 工具                       |
| ---- | --------------- | ------------------------ |
| 资源隔离 | 多个代理共享工作树互相干扰   | git worktree / Treehouse |
| 状态可见 | 人必须知道每个任务的目标与状态 | 有语义标题的 tmux tab          |
| 统一调度 | 拆任务、监控、恢复、汇总 PR | First Mate               |

表格里出现了几个课程里的名词，先拆开解释：

- **git worktree**：同一个 git 仓库可以拉出多个互不干扰的工作目录——每个 worktree 有自己独立的文件和分支，共享同一份对象库。多个代理在同一目录改文件会互相踩踏，各占一个 worktree 就互不影响了。它比完整 clone 更轻，但仍提供文件系统级隔离。
- **资源池（resource pool）**：worktree 如果用完即弃，创建、标记、回收全是手工活，很快变成管理债。资源池的思路是把 worktree 变成可申请、占用、释放、复用的"执行槽"——Treehouse 就是干这个的：自动申请新鲜 worktree、标记占用状态、识别空闲并优先复用。关闭 tab 后自动释放是 Treehouse 的行为，不是 git 原生能力。

视频里 First Mate 的定位值得记住：它不是"第四个写代码的代理"，而是一个**调度入口**——理解跨项目目标、拆成独立任务、建会话、分 worktree、启动执行代理、调验证、整理 PR，交给人最终判断。编排必须包含失败检测与恢复：首次 dispatch 失败时，调度器要能看到"没有任务真正启动"并显式重试。

对当前阶段的我来说，单代理 + 长任务边界已经够用；并行是下一步的方向，先理解原理，需要时再引入。

## 八、总结：高频命令卡与快捷键卡

### 8.1 高频命令卡

```
导航         z xxx / zi / y
搜索         fd xxx / rg "xxx" / fzf
Git          git status / git diff / git diff --stat
             git branch --show-current / git log --oneline -10
tmux         tmux ls / attach -t NAME / new -s NAME
             kill-session -t NAME / kill-server
```

### 8.2 高频快捷键卡

```
WezTerm      Alt+W → Space(Launcher) / p(Palette) / c(新Tab)
             \ 左右分 / - 上下分 / h j k l 移动 / z Zoom / x 关闭
tmux         Ctrl+A → c(新Window) / | 左右 / - 上下 / h j k l 移动
             z Zoom / d Detach / r Reload
Yazi         h j k l 导航 / Enter 打开 / Space 选择 / a 新建
             r 重命名 / y 复制 / x 剪切 / p 粘贴 / d 删除 / q 退出并 cd
```

### 8.3 不知道该用哪个工具时

| 问题 | 答案 |
|------|------|
| 我要换 Windows/Ubuntu 环境 | WezTerm |
| 我要管理项目现场 | tmux |
| 我要去某个熟悉目录 | z |
| 我记不清具体目录 | zi |
| 我要看看文件结构 | y |
| 那个文件在哪 | fd |
| 哪个文件包含这段代码 | rg |
| 我忘了 WezTerm 功能 | Alt+W → p |
| 我暂时离开 Linux 项目 | Ctrl+A → d |
| 我要真正杀掉 tmux 项目 | tmux kill-session -t NAME |

## 九、结语：瓶颈上移，从水手到船长

视频结尾有一句话很值得反复读：

> 瓶颈正在转移。作为船长，你必须跟上——把更多精力放在理解什么重要、与用户交谈、理解竞争格局，并绘制一张把船带向正确方向的藏宝图上。这样，你就从一名水手变成真正的船长。

工具搭船，上下文招募船员，验证与隔离扩大执行力；而**用户洞察、方向判断和最终责任**才让这艘船驶向值得去的地方。成熟的人机协作不是人退出，而是人的工作上移——从逐个 babysit 代理，转向维护目标、优先级和最终判断。

对现阶段的自己：终端工具链已经冻结，不再继续收集工具；接下来的日常是**练熟这套 workflow**——打开终端选环境，z/zi/y 进目录，tmux 组织项目，fd/rg 搜索，Agent/Test/Server 各占一个 Pane 长期运行。船已经造好，剩下的交给航程。
